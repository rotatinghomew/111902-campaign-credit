# 咨询归因与采购结算

本地合成业务资料。人名标识、去向、机构和观测均为虚构，不接入外部系统。

## 输入约定

`data/supplies.json` 以表名组织记录；`data/fields.json` 列出字段及该资料出现的值类型。

`appointments` 的计数单位是一个有效预约，问询不是转化；资料规定取消窗口含截止时刻，之后才可确认可兑现。`links` 是是否可在触点和预约之间建立联系的审计凭据，「候选」不等于确认，「排除」不参与，确认的 `same_person` 可能把两个触点证据归为同一关联对象。汇总触点只提供按渠道/片区/时间的容量上界，不能独立兑现；自然入口仅在有明确非采购联系证明或渠道都不可归属时计为确定自然。所有渠道时间窗以触点日期到预约日期自然日表示，地区须相同，同一排他组中对一笔转化只允许一个渠道认领，转化最多兑付一次。
合同金额元保留到分。合同保底为独立的素材交付款，仅在有交付证据且不超金额上限时支付；转化阶梯按数量累进，以 `upto` 为该档最高计数，`rate` 为本档单条金额。`period_cap` 为同合同从签订到 `cap_through` 的累计上限，`portfolio_cap` 是共享预算；留置份额等归因争议解除且取消窗口结束才可释放。`paid` 是已结算事实；若事实更正不再支持已结值，只提追调范围，不改历史款项或自动付款。

## 口径与处理原则

口径是**合约约定的预约归属范围，不等同于渠道因果增量**。实现严格遵守：

1. **资格约束**：同地区、触点到预约自然日在合约 `max_days` 窗内、关联边非「排除」，三者同时满足才进入候选。
2. **证据分级**：独立触点+确认关联才可独立兑现（`confirmed`）；独立触点+候选只进可能集合（`candidate`）；汇总触点永远只是容量上界（`bound_only`），不能独立兑现，也不能补给最缺业绩的渠道。
3. **排他与一次兑付**：同一排他组内一笔转化只允许一个渠道认领；同一 `same_person` 的多份回执不就近拼接成多份贡献。
4. **可辩护场景**：对每个仍有效且过取消窗口的预约，枚举其全部强证据落点，做笛卡尔积形成场景；每个场景里每预约最多兑付一次。各渠道上限取自各自最有利场景，**不能相加同时承诺**；另给全组合计边界。
5. **不确定性登记**：撤销/未过窗口/证据不足/同人争议/自然入口分别登记可能集合、容量上界与“哪些材料能缩小范围”。
6. **自然预约**：有可归属采购证据时不能计确定自然；只有明确非采购证明或全部渠道不可归属时，才排除在付款之外。
7. **资金三档**：可明确支付的素材保底款；无论合理归属如何都至少应付的贡献款（跨场景现金下限，为 0 即不得预支）；留置与冻结等争议准备。留置按合约比例从每笔贡献中拆出，不把有凭据部分全压到争议结束。
8. **预算与缺口**：期间上限与共享预算逐场景核算；已明确应付款超过可用预算时报告缺口并列全部债务，不按顺序抹账。
9. **只追加**：已确认付款不删改，凭据失效只列追调范围、预算在收回前不恢复；已释放留置不能当作没放出去；重判只追加事件，并区分“证据争议已解决但共享预算未恢复”与“依据本身失效”。

## 代码结构

- `attribution/sources.py`：资料读取、按 `recorded` 折叠修订、as-of 视图、付款期间/显式排除。
- `attribution/rules.py`：窗口、地区、证据分级、同人合并、自然排除。
- `attribution/scenarios.py`：可辩护场景枚举、条数上下限、不确定性登记。
- `attribution/money.py`：累进阶梯、留置拆分、保底、预算上限与缺口、付款回查、出纳三档。
- `attribution/engine.py`：汇总一次结算运行快照（含来源/运行双重哈希）。
- `attribution/ledger.py`：只追加本地台账（运行快照、提案事件流、审批、支付、重判）。
- `attribution/report.py`：主管与出纳共用的中文 Markdown 报告。
- `settle.py`：命令行入口。

## 操作入口

在 Linux 上使用 Python 3.11 及标准库，无需第三方包。建议用 `-I` 运行：

```bash
# 生成 as-of 运行快照与 Markdown 报告（结果写入本地 ledger/，已 gitignore）
python3 -I settle.py run --as-of 2026-11-19

# 历史重建：paid 无事件日期，按外部付款日历显式排除当时尚未发生的付款
python3 -I settle.py run --as-of 2026-10-25 --exclude-paid P01 P02 P03

# 提案（落点必须存在于某可辩护场景，否则拒绝；不得就近拼接关联）
python3 -I settle.py propose --as-of 2026-10-25 --appointment A2 --contract C2
python3 -I settle.py approve --as-of 2026-10-26 --proposal-id PR-001
python3 -I settle.py pay     --as-of 2026-10-27 --proposal-id PR-001

# 审批后收到撤销预约或同人第二份回执：用新视图重判提案与留置是否仍成立
python3 -I settle.py run     --as-of 2026-11-19
python3 -I settle.py rejudge --as-of 2026-11-19 --proposal-id PR-001

python3 -I settle.py proposals          # 查看提案事件流折叠状态
python3 -I settle.py trace --as-of 2026-11-19   # 已付款回查
```

`ledger/runs/` 是不可变运行快照（同 as-of 同内容自动复用），`ledger/proposals/proposals.jsonl` 是只追加事件流，`ledger/reports/` 是 Markdown 报告。

## 资料检查与测试

```bash
python3 -m unittest discover -s tests -v
```

`tests/test_sources.py` 检查表字段、类型和关键关联；其余测试覆盖窗口/地区/证据分级、场景枚举与一次兑付、阶梯与留置、预算缺口、as-of 折叠、只追加台账以及撤销/同人回执/预算未恢复三类重判。当前仓库的分析结果只落在本地 `ledger/`，不回写来源资料。
